# BLINDSPOT privacy and accessibility notes

This document describes the actual plugin data flow, not a blanket legal compliance claim. The deployment owner must assess GDPR, ePrivacy, applicable educational-sector rules, contractual arrangements and the actual model provider. Internal engineering follows the BASE3 privacy and WCAG 2.2 AA requirements, but independent deployment verification remains necessary.

## Personal data processed and stored

The existing host authentication identifies the native user; `IAuthorizationService` decides whether they can play. BLINDSPOT saves one match document per row in the existing `blindspot_matches` table. The row contains a random match ID, host authority, trusted native user ID, revision, timestamps and a JSON match payload.

The payload stores a privately selected five-theme plan (agent-reported document titles, subject labels and optional section names), the current subject, a generated thesis and hidden solution, score, round and game phase. During interrogation it also stores the player's **free-form questions** and the agent's replies in the current round so that players can resume safely and the next agent invocation has the actual dialogue. After that round the live dialogue is replaced for the next round. Finished-round records retain the player's **written accusation**, the generated thesis, the judgement result, correction, optional model-supplied source label, number of questions used and points. Personal best and completed match history are derived from these existing match rows, not held in a separate tracking database.

The player should not enter personal, sensitive or confidential third-party information in free text. The game does not require such information. No advertising or third-party analytics are added by this plugin. The code does not add cookies or local-storage settings. User interface animation reduction applies to the current page only.

## Model and document flow

The already configured MissionBay agent (`blindspot.opponent`) receives four kinds of requests through `IAgentExecutionService`: a one-time topic inventory from its existing attachments, a challenge for one server-selected document/theme label, interrogation of the current claim and final judgement. The game selects five labels from the agent-returned inventory but never lists, fetches, opens or validates attached files or PDF metadata itself. The defense request contains the visible thesis and current dialogue but deliberately omits the hidden flaw and correction. The judgement request receives those private values to evaluate the final accusation. Each request has its own system instruction, sent through the existing execution API. A short optional reference label generated by the agent can be retained in a finished-round record. No plugin-owned PDF manager, second retrieval path, LLM provider or chat-history memory is introduced.

The model may be operated by another provider. Model input, output, transport, logging, retention, possible training, hosting region and international transfers depend on the effective provider and MissionBay configuration and have not been audited here. Model-provider copies, logs and backups are not erased by the plugin's database deletion operation. BLINDSPOT supplies an execution channel label but no match-scoped `conversation_id`; it does not send completed-round claims or transcripts when generating new rounds. The private five-theme plan is retained with the match, not sent wholesale on each subsequent model call. Only the active round dialogue is included in question and judgement requests. Any memory separately enabled on the configured MissionBay agent remains controlled by that agent and its runtime, not by BLINDSPOT.

## Authorization, disclosure and deletion

Each server action rechecks the trusted host user and requires an explicit positive `IAuthorizationService` decision. The database owner and authority scope are applied to all match queries and modifications. Optimistic revisions prevent duplicate game-state commits. Failed authorizations, invalid model responses or a stale revision do not create a successful saved transition; parallel model requests may nevertheless consume provider tokens.

Before an accusation is committed, the browser only receives the visible thesis, the previous questions/responses, the remaining question count and score, never the private hidden flaw or correction. After the answer is judged, the correction and optional source label are visible. Source labels and the agent's semantic grading are not independently verified against PDF bytes.

The **Delete my matches** action deletes all rows for the current host authority and native user ID, including existing history, theme labels, scores, free-form questions and accusations. There is no automatic expiry period. Records persist until user deletion or an authorized operator cleanup. Database backups and external provider records require separate deletion and retention policies. Uninstalling the plugin does not automatically erase its table or the existing agent's knowledge files.

## Accessibility and operational verification

The user interface uses labeled textareas, native buttons, keyboard-visible focus, status/error announcements, a non-timed game loop, responsive sizing, and a reduced-motion switch plus the OS `prefers-reduced-motion` preference. The conversation and correction are presented as text as well as through visual effects. All 12 supported UI language catalogs (`ar`, `bg`, `de`, `en`, `es`, `fr`, `hi`, `it`, `pl`, `pt`, `ru`, `zh`) are supplied in this plugin's `lang/Display/` directory. The execution-time game instructions request German model-generated content. The localized activity panel for agent interactions is entirely client-side; it adds no telemetry, polling, timers or persistence. Starting a match now makes one additional ordinary agent execution to prepare the theme inventory before the first thesis. The fullscreen control uses the browser's native API; both controls are keyboard operable, and the activity display is text-announced without relying on its animation. Real keyboard, zoom, contrast, touch, screen-reader and embedded-host tests are needed before declaring WCAG 2.2 AA conformance.

The operator should also test actual ILIAS authorization and session revocation, model behavior against the currently attached documents, correctness of the dynamic challenges and semantic scoring, concurrency, provider timeouts, model costs, provider data handling, database deletion and backup retention, and performance under representative users. Locally passing syntax and contract tests are not proof of production readiness.
